# 外部自动化项目调研

- 日期：2026-10-19
- 调研对象：GitHub 公开 README、CLI 文档和输出规范
- 调研方式：只读公开资料；没有运行外部项目，没有导入登录态，没有访问或采集任何平台账号
- 结论状态：调研完成，形成下一阶段控制面方向

## 1. 核心结论

成熟项目并没有把“受限平台全量历史抓取”变成安全能力。它们把系统拆成三层：

1. **能力边界**：公开源走自动 adapter；受限源要求显式登录、人工触发或平台导出；Agent 只拿到窄工具。
2. **运行可靠性**：任务注册表、持久队列或游标、原始快照、归一化数据、幂等身份、分类错误、退避 / 冷却、重启恢复和运行审计。
3. **人的工作流**：到期提醒、变化摘要、待人工动作、一次点击打开目标页面、采集后自动拆解候选，以及发布前人工确认。

对本项目最有价值的改造不是新增更激进的爬虫，而是补一个**采集指挥中心**：每个对标账号都有下一步动作、覆盖率、失败原因、可恢复任务和能力边界。自动部分在后台跑，受限部分明确排队等人，采集完成后立即给出“新增几条、重复几条、缺口多少、下一步是什么”。

## 3. 值得固化的通用模式

### 3.1 统一采集结果信封

catbus 的输出规范最适合借来做内部 API 契约：

```json
{
  "ok": true,
  "sourceId": "source-1",
  "method": "browser-assisted",
  "found": 42,
  "created": 3,
  "duplicates": 39,
  "blocked": 0,
  "coverage": { "collected": 42, "displayed": 50, "status": "partial" },
  "nextAction": "continue-scroll-and-capture",
  "cursor": "opaque-cursor",
  "error": null
}
```

失败时不返回空 success，而是给出 `AUTH_REQUIRED`、`NOT_IMPLEMENTED`、`RISK_CONTROL`、`NETWORK`、`UPSTREAM`、`USAGE` 等分类。对单人工作台来说，不需要照搬退出码，但错误必须能直接翻译成下一步动作。

### 3.2 指挥中心

参考 changedetection.io、creatorhub 和 Agent Reach，账号页下一版应该从“账号列表”升级为采集控制面：

- 每个账号显示：平台、采集方法、能力状态、下次运行、覆盖率、最近错误、冷却状态。
- 自动源显示：最近成功时间、新增数、重复数、原始快照入口。
- 受限源显示：待人工动作、“打开主页”按钮、采集书签、目标范围和已加载范围。
- 任务意图持久化：服务重启后仍知道哪些账号今天应检查、哪些补采未完成。
- 采集完成立即显示摘要：新增、重复、失败、覆盖率变化、进入 Inbox 的数量、建议拆解对象。
- 每个平台一张能力矩阵：支持列表、详情、评论、正文、媒体、登录要求、数据口径、风险边界。

### 3.3 快照与差异

changedetection.io 的价值不在抓得多，而在能解释“什么变了”。本项目已有 raw snapshot，下一步应补：

1. 快照摘要：账号、内容数、互动数、最新发布时间、内容指纹。
2. 与上次快照对比：新增条目、互动变化、标题变化、疑似删除。
3. 只把有意义的变化推给晨报，避免“有变化”但没有判断价值。
4. 保留原始证据但限制展示长度，超大文本和媒体走外置目录。

### 3.4 风险状态

creatorhub 的保守模式可以轻量吸收：

- 同一 source 串行执行，已有 singleton 基础。
- 连续网络失败、403 / 429 / 登录页、空结果和超时分别计数。
- 连续失败后进入冷却，冷却结束先做低频探测。
- `RISK_CONTROL`、验证码和访问受限不允许自动重试，必须人工处理。
- 自动任务只访问公开源；受限源只生成待人工队列，不启动隐藏浏览器。
- 配额按 source 和方法计算，而不是全站共享一个模糊频率。

### 3.5 Agent 边界

xiaohongshu-mcp、catbus 和 Agent Reach 都说明：强项目给 Agent 的不是自由聊天，而是窄工具和自描述能力。

本项目 Agent 工具应分三类：

1. **安全读取**：读取本地素材、选题、快照、晨报和任务包。
2. **候选生成**：拆解、提纲、口播稿、标题、平台文案、视觉方案；结果一律待人工确认。
3. **受限动作**：打开页面、生成采集书签、准备发布包；默认必须用户点击确认，不自动发布、点赞、评论或私信。

### 3.6 发布流水线

social-auto-upload 的经验是：上传是高频、重复、规则明确的动作，可以脚本化；但平台限制、登录态和验证码不能被隐藏。本项目后续应先落：

1. 每平台发布规格校验：文件格式、大小、标题长度、话题、封面、正文。
2. 生成可复制发布包：视频、封面、标题、描述、话题、证据核对记录。
3. 台账记录：待发、已复制、已上传、失败原因、重试动作、发布链接。
4. 只有当连续多条内容都稳定人工发布后，才评估对最低风险平台做“填充表单 + 人工提交”的半自动化。

### 3.7 证据包 / 归档包

ArchiveBox、Karakeep、SingleFile、yt-dlp 和 gallery-dl 的共同经验是：先保住证据，再谈整理。对高价值信号和热评，工作台应支持一个分层证据包：

```text
evidence/<signal-id>/
  meta.json              # 结构化元数据、能力口径、采集时间和可见范围
  raw.json | raw.txt     # 采集入口返回的原始数据或快速粘贴原文
  page.html | singlefile # 可选：高价值争议内容的原文证据
  screenshot.png         # 可选：人工可见状态截图
  media-manifest.json    # 图片、视频、音频链接与下载状态
```

规则：

1. 结构化对象继续进 `data/workbench.json`，证据包和媒体文件外置到本地 evidence 目录或用户显式选择的 Drive 目录。
2. Git 只保存模板和清单，不保存真实证据、素材、账号和媒体。
3. `unknown` 必须保留，不能为了显示 complete 编造总数。
4. AI 标签、摘要、数据口径和拆解永远是候选，人工确认后才进入事实字段。
5. 媒体下载使用 archive 式幂等记录，重复任务只补缺失文件，不重复下载。

## 4. 与当前实现的差距

当前项目已经具备轻量调度、失败退避、同源并发保护、投递箱、快速粘贴、公开页面解析、多层去重、晨报、Agent 任务包和备份。对照外部项目后，主要差距是：

1. **没有采集指挥中心**：用户看到账号和状态，但缺少“今天该补哪个、从哪里继续、为什么卡住”的任务视图。
2. **结果契约不够统一**：不同入口的返回字段和错误语义还不够一致，空结果和失败的留痕边界需要补齐。
3. **能力矩阵未显性化**：X、小红书、抖音、公众号分别能自动拿到什么、不能拿到什么，页面没有一张可信表。
4. **无 typed error / doctor**：失败能记录，但还不能一键体检环境、网络、路径、Drive、Agent 和每个 source adapter。
5. **快照有留存但差异不足**：尚不能清楚回答“这个账号自上次采集后新增了什么、互动涨了多少”。
6. **历史运行和大文本没有保留上限**：长期使用会把 `collectionRuns`、`rawSnapshots` 和 Agent 结果撑大。
7. **公开 feed route 管理不足**：RSS / 公开页面可以跑，但还缺 route 配方、能力和失败替代方案。
8. **证据包未分层**：重要内容缺少原文、截图、原始数据和媒体清单的长期归档格式，链接失效后难以复核。
9. **可见范围导出不足**：X、抖音、公众号还没有像小红书书签一样明确“用户加载多少、系统导出多少”的通道。

## 5. 实施优先级

### P0：采集指挥中心

- 建立源级 pending intent：待检查、待人工、待补采、冷却中、失败、完成。
- 展示覆盖率、最近摘要、失败分类和下一步动作。
- 采集后返回统一信封，并保留空结果运行记录。
- 支持从待办直接打开主页 / 复制书签 / 查看快照。

验收：用户只看指挥中心，就能知道今天每个对标账号该做什么；重复采集后能解释新增和重复。

### P1：结果契约与能力矩阵

- 内部采集统一 `{found, created, duplicates, blocked, failed, coverage, nextAction, cursor, error}`。
- 错误分类到登录、风控、网络、解析、能力缺失、参数错误。
- 页面展示四平台能力矩阵，不支持的项明确写“不伪装支持”。

验收：新增 adapter 必须先声明能力和结果契约；失败能直接生成下一步动作。

### P1：证据包与可见范围导出

- 为高价值信号和热评生成分层证据包目录，结构化对象只保存索引。
- 媒体下载记录 manifest 和幂等 archive，大文件不进 Git。
- 受限平台补“手动加载范围 + 显式导出”入口，能力矩阵明确 unknown / partial / complete。

验收：一条信号可以从工作台跳到原始数据、原文或截图证据；重复采集不会破坏证据包。

### P1：快照差异与晨报增强

- 每个账号保存最近快照摘要。
- 计算 新增 / 重复 / 互动变化 / 疑似删除。
- 只把有信号价值的变化推入晨报。

验收：晨报能回答“哪些对标账号有新增，新增内容中哪几条异常”。

### P2：轻量 doctor 与保留策略

- 检查本机服务、数据文件、备份目录、投递箱、Drive 镜像、Agent 命令、公开网络和 adapter 状态。
- 对运行记录、快照和 Agent 大文本设置默认保留数与归档策略。

验收：一键体检能列出每个能力“可用 / 待配置 / 不可用 / 有风险”。

### P2：发布包先行，不先接自动上传

- 每平台生成文件名规范、封面、标题、描述、话题、素材清单和检查项。
- 发布台账记录人工动作和失败原因。

验收：一条视频可以按平台逐项复制、上传、登记，不遗漏证据核对。

## 6. 明确不做

即使外部项目提供实现，本项目生产链路也不引入：

- 登录态后台抓取第三方账号。
- 自动滚动、自动翻页、隐藏浏览器监控。
- 平台私有接口调用、签名复现、验证码识别。
- 代理池、浏览器指纹伪装、限流规避。
- 自动点赞、评论、私信、关注。
- Agent 自主发布或删除内容。
- 把“抓到多少”当成“全量”；未知总数必须显示 unknown。

这些边界不是保守姿态，而是保护用户账号和证据可信度的产品规则。
