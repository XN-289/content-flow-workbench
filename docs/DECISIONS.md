# DECISIONS — 设计与工程取舍记录

规则：**每次 UI 或架构改动都追加一条**。格式固定，方便后续 AI 快速理解「为什么是这样」。

---

## D-001 2026-10-21 · 桌面工作台采用「队列 / 主画布 / 检查器」三区结构

- **做了什么**：总览与工作流改为 260px 队列 + 1fr 主画布 + 300px 检查器；历史、证据、风险进入检查器，不再平铺在长页。
- **为什么**：`handoff/UI_AUDIT.md` 指出工作流桌面仍有 3,202px、纵向堆叠是主要复杂度来源；三区结构让「当前对象」成为稳定上下文。
- **放弃了什么**：放弃「一屏展示全部模块」的信息全量展示；放弃把详情继续折叠进主画布。

## D-002 2026-10-21 · 层级改用表面阶梯 + 发丝边框，静态卡片禁用阴影

- **做了什么**：引入 `--canvas / --surface / --surface-sunken / --surface-hover` 四级表面阶梯；阴影仅保留 `--shadow-overlay` 给浮层。
- **为什么**：旧界面「白面板 + 细边框 + 统一圆角」缺乏层级识别；Linear 的做法用阶梯代替投影，可读性更稳且深色模式更好扩展。
- **放弃了什么**：放弃柔和投影带来的「浮起」装饰感。

## D-003 2026-10-21 · 状态拆为四族 + 演练中性，颜色只作第四重编码

- **做了什么**：对象状态（成功）、运行状态（待人工）、阻塞状态（受阻/失败）、候选状态（待分诊/unverified）、演练/中性五组固定 token，并规定状态必须「颜色 + 文字 + 位置」三重表达。
- **为什么**：`本地演练 / blocked / 待人工 / unverified` 是产品的诚实语义，不能被合并或弱化。
- **放弃了什么**：放弃只用色块区分状态的旧做法。

## D-004 2026-10-21 · 移动端重新定义任务顺序，而非折叠桌面两列

- **做了什么**：390px 首屏只保留「晨间状态 → 今天先做什么 → 当前选题」，底部固定唯一主行动，其余进全屏 Sheet。
- **为什么**：旧移动端工作流仍需 4,496px 滚动，触控目标与阅读密度都不合格。
- **放弃了什么**：放弃移动端「信息全量可达」的旧目标，改为按任务分步。

## D-005 2026-10-21 · 前端选型：Vite + React + TS + Tailwind v4 + Radix/shadcn 代码自持

- **做了什么**：确定技术栈与目录结构，明确 P0–P8 分阶段迁移，`app/app.js`、`app/styles.css` 在 P8 删除。
- **为什么**：单文件模板字符串渲染是设计债务的放大器；token 写在 CSS（`@theme inline`）让改一个变量全局生效，也便于后续 AI 稳定迭代。
- **放弃了什么**：不选 Mantine/MUI（视觉会被库默认值绑架）；不选纯 CSS-in-JS（与 token 单一来源冲突）。

## D-0062026-10-21 · 实际落地改为「Vite + React + 纯 CSS token + 独立 UI 服务」，不改主服务

- **做了什么**：新增 `web/`（React 19 + TS + Vite 6）、`scripts/build-ui.mjs`、`scripts/ui.mjs`；构建产物写入 `app/ui-<时间戳>/`；主服务 `scripts/server.mjs` 零改动，新界面通过代理复用其 API。
- **为什么**：本执行环境禁止覆盖/删除既有文件（`app/index.html`、`app/dist/*` 均 EPERM），既无法把新产物写回原路径，也无法让主服务改指向；时间戳目录 + 代理服务是唯一既能“直接可用”又不破坏现有系统的方案。同时 Tailwind 的 `@theme`/`@theme inline` 深色模式坑在纯 CSS 变量方案下不复存在。
- **放弃了什么**：放弃“单端口 5177 直接换新界面”的理想形态；旧界面保留在 5177 作为回退，等具备文件修改权限时再合并。

## D-0072026-10-21 · 对抗性检验优先于“看起来没问题”

- **做了什么**：用脚本断言（横向溢出、触控目标、控制台错误、键盘顺序、深色切换）+ 逐张截图目视，做了三轮检验；发现并修复 5 个真实缺陷与 2 个工程性陷阱。
- **为什么**：首轮截图显示桌面端“很像样”，但移动端存在导航压内容的严重布局缺陷，且 390px 下信息流横向溢出 537px——这些在桌面截图里完全看不见。只靠目视会漏。
- **放弃了什么**：放弃“先交付再补测试”的顺序；UI 验证脚本从本轮起与设计契约一起维护（`work/ui-verify.mjs`），规则变化时同步改断言。

## D-0082026-10-21 · 空数据下不允许出现“看起来已完成”的结论

- **做了什么**：优先级列表只渲染真实存在的待办；没有进行中的选题时，人工关卡显示“不适用 / 没有进行中的选题”而不是绿色“完成”；证据包为 0 时不再挂 unverified 标签；Inbox 行内主行动只给“下一条该处理的信号”，其余行降级为次级动作。
- **为什么**：空态检验（`SCENARIO=empty`）暴露出“0 个任务也显示已完成”这类误导——诚实性缺陷比缺功能更严重。
- **放弃了什么**：放弃“每行都给主按钮”的便利性，换取焦点唯一。

## D-0092026-10-21 · 失败必须给出原因与下一步

- **做了什么**：`/api/state` 失败时展示 HTTP 状态码 + 三步排查（主服务是否运行、API 端口是否一致、端口是否被占用）+ 重试按钮；写操作失败沿用服务端原始错误文案。
- **为什么**：原先只显示“无法连接本地服务”，用户无法判断是服务没起还是端口配错。
- **放弃了什么**：不在前端猜测服务端内部原因，只呈现可核实的事实与排查路径。

## D-0102026-10-21 · 验证脚本与假数据服务随代码进仓库

- **做了什么**：`work/ui-verify.mjs`（回归断言）+ `work/ui-fixtures.mjs`（empty / minimal / error 三种假数据，只读状态、空写接口）纳入项目；截图与报告落在 `work/verify-shots/`、`work/verify-reports/`。
- **为什么**：验证脚本放在会话目录里等于没有——换个人、换个会话就丢了；假数据服务保证空态与失败态可以被反复验证，且**物理上不可能改动真实数据**。
- **放弃了什么**：不引入 Playwright 浏览器下载（复用本机缓存的 Chromium，避免数百 MB 下载）。

## D-011 2026-10-22 · 成品前端收敛为 React + 纯 CSS token + 5177 单端口（Supersedes D-005 / D-006）

- **做了什么**：当前成品采用 React 19 + TypeScript 5.7 + Vite 6 + 纯 CSS token；源码只改 `web/src/**`，构建稳定输出到 `app/dist`。`scripts/server.mjs` 在 5177 单端口同时托管 React 页面与 `/api/**`，四个工作域使用 `/`、`/flow`、`/workflow`、`/system` 浏览器路径，并由 SPA 回落承接刷新与深链。`scripts/ui.mjs`、`scripts/ui-server.mjs` 与 `app/ui-*` 时间戳产物不再是成品入口。
- **为什么**：D-005 中计划使用的 Tailwind、Radix、shadcn 最终没有落地；D-006 为解决临时写入限制而采用的独立 UI 服务、时间戳产物与代理链路也不应固化。单端口让部署、验收和故障排查只剩一个进程和一份稳定产物，同时纯 CSS token 更容易审查主题与状态语义。
- **放弃了什么**：放弃 D-005 的组件库与 `@theme` 方案，放弃 D-006 的双服务、独立 UI 端口和时间戳目录方案。历史决策保留，用于解释演进原因，但不再描述当前成品。

## D-012 2026-10-22 · UI 验收工具保持本地，构建产物必须可复现且无历史残留（Supersedes D-010）

- **做了什么**：`work/ui-verify.mjs`、`work/ui-fixtures.mjs` 继续作为本地验收工具，不声称已进仓库；`work/` 和 `handoff/` 仍不进入 Git。`npm run build:ui` 先清空 `app/dist`，再由 Vite 生成当前资源并回填 `capture-bridge.html`，避免多轮 hash 文件堆积。
- **为什么**：本地验收工具依赖本机 Chromium 与现有 fixtures，直接公开会把未锁定依赖伪装成可复现测试；而稳定产物目录比测试脚本位置更直接影响运行和发布。
- **放弃了什么**：放弃“验证脚本已随代码进仓库”的错误表述，也放弃用 `emptyOutDir: false` 保留历史构建文件的旧做法。

## D-013 2026-10-22 · 本地 main 与 GitHub main 是唯一源码，临时分支必须通过机器门槛合入

- **做了什么**：定义 `D:\personal-content-workbench` 的 `main` 与 GitHub `origin/main` 为唯一最终源码；Agent 使用临时分支或仓库外 worktree，集成者按分支顺序合并并在推送后执行 `npm run verify:source`。门槛检查脏 worktree、stash、冲突标记、worktree / 分支未合并提交，以及本地、`origin/main`、GitHub 实时 `main` 的 SHA 一致性。
- **为什么**：多 Agent、多 runtime 并行时，最终风险不是单个提交本身，而是代码留在未合并分支、另一个 worktree、stash 或本地未推送提交中。口头交接无法可靠证明最终源码，必须让“本地与 GitHub 同一主线”成为可执行验收条件。
- **放弃了什么**：放弃各 Agent 各自维护长期副本、直接写 `main`、依靠人工记忆合并分支，以及用强制推送或整文件覆盖制造“表面无冲突”的做法。

## D-014 2026-10-22 · 逐字稿改为后台运行 + 宽版阅读器，ASR 结果始终显式标记候选

- **做了什么**：`POST /api/signals/transcript` 支持 `background: true`，立即持久化 `running` 占位并异步执行 ASR，进度写入阶段；同一 `runId` 完成时原位替换，不重复插入。前端每 3 秒轮询运行中的逐字稿，只在首次进入终态时提示一次。已捕获内容通过宽版 Sheet 提供全文 / 时间轴、复制和 TXT / JSON 下载。
- **为什么**：真实转写可能持续数分钟，同步请求会占住交互并让用户误以为页面失败；同时已有真实逐字稿只能在运行记录里看到“转写媒体”，无法被阅读、引用或带走，链路实际上没有闭环。ASR 的同音字与术语错误必须持续以 `unverified` 呈现，不能因“已生成”伪装成已校验。
- **放弃了什么**：保留未传 `background` 时的同步行为作为旧调用兼容回退；放弃为逐字稿伪造“成功”状态、放弃把全文塞进主画布或复制到公开仓库，也放弃用时间戳多文件快照增加轮询复杂度。

## D-015 2026-10-22 · 封面进入信息流和逐字稿阅读路径

- **做了什么**：信息流信号行增加 3:4 缩略封面，逐字稿宽版阅读器头部增加同源封面；图片使用 `referrerPolicy="no-referrer"`，加载失败时直接隐藏。
- **为什么**：用户判断对标内容时需要同时看到标题、封面和逐字稿。此前封面虽已进入证据包，却被藏在数据层，阅读路径无法直接核对画面与标题的关系。
- **放弃了什么**：不把远程图片下载进仓库，不做图片代理，不保存平台 Cookie 或登录态，也不因为已有封面就推断内容已经人工校对。

## D-016 2026-10-22 · 本地 Agent 插件只暴露声明式、loopback 内容能力

- **做了什么**：新增 `plugin/content-flow-workbench/`，以 manifest 和 Node ESM 客户端向 gkbot、Muse、Codex、Claude、Cursor 暴露九个固定方法；客户端只接受 loopback URL、manifest 内 `/api/**` 路由，拒绝 URL path / query / hash、URL 凭据和 HTTP 重定向。
- **为什么**：工作台能力需要能被其他 Agent 复用，但不应让宿主直接拼任意工作台 URL、读取浏览器登录态或绕过人工关卡。把发现、origin 校验和路由白名单集中在客户端，才能让分发后的调用边界可审计。
- **放弃了什么**：不提供通用 HTTP 代理、不把 Cookie、capture token、浏览器 profile 或平台签名交给插件；插件可以采集、分析和建任务，但不能替用户发布或把候选升级为事实。

## D-017 2026-10-22 · 全文逐字稿与时间轴是一等证据，Agent 必须拿到完整上下文

- **做了什么**：单条公开视频可显式运行本地 faster-whisper ASR，保存全文、时间轴、模型、时长和运行记录；宽版阅读器提供全文 / 时间轴 / 分析、复制和 TXT / JSON。通过 `signalId` 创建 Agent 任务时，任务包自动带入完整逐字稿、分段时间戳、ASR 模型和证据边界。
- **为什么**：只知道标题、封面或正文摘要无法解释口播内容的钩子、节奏、承诺兑现和留存机制。逐字稿是后续分析的原始对象，不能被截断成一段摘要后交给 Agent，也不能在复制过程中丢失时间轴。
- **放弃了什么**：不使用正文、标题或平台字幕链接伪造逐字稿，不把 `.m4s` 分片当完整视频，不把 ASR 候选稿直接标为已校对；全文和时间轴保持本地私有，真实内容不进入 Git。

## D-018 2026-10-22 · 候选分析默认 `unverified`，Drive 使用显式本地同步导出

- **做了什么**：逐字稿分析输出钩子、结构、节奏、留存机制、情绪回报、作者基线和时间戳引文，并以输入哈希复用；知识导出通过 Google Drive 桌面同步目录写入 manifest、Markdown / JSON、README 和 SHA-256，且只在用户显式触发时执行。
- **为什么**：用户需要 AI 给出更详细、可复用的爆款假设，但平台数据、逐字稿和启发式推断不是同一种事实。显式导出既能让 gkbot / Muse 等 Agent 共享知识，又不引入 OAuth、API Key 和后台隐式上传。
- **放弃了什么**：不把启发式分析说成平台流量因果证明，不自动把 Agent 结果导入终稿，不保存 Google API Key 或 OAuth token，不把任务内容静默同步到云端；真实 Google Drive 和外部 Agent 回流仍需单独做一次人工接入验收。

## D-019 2026-10-22 · 系统页展示只读知识包历史，不把“导出完成”写成“已验证”

- **做了什么**：系统页新增最近 12 次知识包导出记录，展示完成时间、拆解数、逐字稿数、文件数、本机目标路径，以及独立的 `completed` 与 `unverified` 状态。
- **为什么**：导出已经能写入 Google Drive 桌面同步目录，但此前只能在逐字稿阅读器看到一次性结果，系统页无法核对历史、目标路径和证据边界。把记录放回系统页，用户不必重新翻信息流才能确认知识是否真正落盘。
- **放弃了什么**：不在系统页新增隐式导出、删除或重新上传动作，不把本地目录映射写成云端已同步，也不因为文件写入成功就把启发式分析标为 `verified`。Agent 任务、备份和采集记录在窄屏改为容器内横向滚动，不缩小关键操作到不可点击。

## D-020 2026-10-22 · 一键验收只保留高信号输出，单项命令仍可独立定位

- **做了什么**：新增 `scripts/verify-workbench.mjs` 和 `npm run verify:workbench`，顺序执行语法、主链路、后端流水线、信源、批量采集、插件、TypeScript、diff 与 UI 构建；成功只输出 11 行步骤结果，失败才展开对应 stdout / stderr。原有单项 npm 命令继续保留。
- **为什么**：多轮开发中反复手工拼相同命令，既容易漏步骤，也会让终端输出和 Agent 上下文被重复日志占满。统一入口让“完成定义”可执行，同时保留失败时的完整诊断信息。
- **放弃了什么**：不把浏览器、Google Drive 真实目录、gkbot / Muse 宿主接入和 `verify:source` 混进本地代码验收；这些依赖外部运行时或要求干净主线，必须单独验收，不能用 11 步通过替代。

## D-021 2026-10-22 · 链接输入按对象意图分流，批次结果必须持久回显

- **做了什么**：快速粘贴发现链接时统一进入 `/api/source-intake/batch`，由批次入口判断账号 / 主页 / 笔记对象；没有链接的正文和评论仍走 `/api/capture`。信息流左栏新增“最近链接入库”，持续展示最近批次的识别、注册、采集、重复、待处理和阻断原因，单条队列保留可恢复状态。
- **为什么**：一段分享文案可能同时包含账号和多条笔记，逐条盲目采集会把重复、受限和失败藏在一次性提示里。批次身份和持久队列让用户能看见系统究竟识别了什么、为什么没有入库，并在刷新后继续判断下一步。
- **放弃了什么**：不把所有链接都硬塞进详情采集，不把空 `noteId` 的 blocked 卡片伪装成可打开信号，不用 Toast 代替可追溯结果，也不隐藏重复项和受限原因。

## D-022 2026-10-22 · 真实逐字稿链路必须用隔离 E2E 证明，而不是只靠 mock

- **做了什么**：新增 `scripts/transcript-e2e-regression.mjs` 和 `npm run test:transcript:e2e`。测试用 Windows 中文 SAPI 生成短句、由 ffmpeg 合成临时 MP4，预置到临时 `TRANSCRIPT_DIR`，再启动隔离服务执行后台逐字稿、证据包和候选分析全链路；断言真实 ffmpeg + faster-whisper 生成 `captured` 全文与时间轴、同一 run 原位完成、媒体与 JSON 落盘、证据 SHA-256 匹配、分析保持 `unverified` 且按逐字稿哈希复用。
- **为什么**：既有主链路回归主要证明接口和失败边界，不能证明本机媒体处理、ASR 模型、异步状态替换、证据哈希与分析复用在真实执行时能接起来。独立 E2E 用不可访问的 CDN 地址作为诱饵，成功即证明走的是预置本地完整视频路径，而不是网络下载或 mock 文本。
- **放弃了什么**：不把该测试加入默认 `verify:workbench`，因为它依赖 Windows 中文 SAPI、ffmpeg 和本机 faster-whisper 模型；不放宽生产 CDN 白名单、不编写假逐字稿、不读取或修改真实主数据，也不把真实个人媒体写入 Git。

## D-023 2026-10-22 · 选题创建直入工作流，证据生成直入核对，当前选题主卡可编辑
