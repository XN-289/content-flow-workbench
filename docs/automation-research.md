# 自动化调度调研：AIHOT 的轻量吸收

- 日期：2026-10-19
- 参考项目：[KKKKhazix/AIHOT](https://github.com/KKKKhazix/AIHOT)
- 调研结论状态：已落地第一版本地调度器

## 1. AIHOT 做对了什么

AIHOT 的核心不是某个平台抓取器，而是把“信源、计划、执行、健康状态”拆开：

1. 信源统一为 RSS、网页列表、JSON 列表、X 搜索、公众号、外部推送等 adapter。
2. Worker 每分钟检查一次到期信源，执行层不依赖页面渲染。
3. 每个信源有 `enabled`、间隔、下次运行时间、游标、失败次数、健康状态和最后错误。
4. 单个信源失败不影响其他信源；失败用递增退避，成功后恢复原间隔。
5. 同一信源使用 singleton job，避免重复并发执行。
6. 每次运行留痕，管理端可以先预览再确认信源配置。
7. 页面渲染不触发模型和昂贵采集，耗时任务放到 worker。
8. 原始链接和来源信息是一等字段。

这些机制适合单人工作台，因为它们解决的是“忘记跑、坏了不知道、重复跑”的真实问题。

## 2. 明确不搬的部分

AIHOT 是一个完整热点站框架，本项目是本地单人生产工作台，所以不引入：

- Postgres、pg-boss、Docker。
- API、worker、Web 三进程架构。
- Fastify 和独立队列服务。
- AI 打分、总结和发布管线。
- 付费 provider 集成和复杂预算回执。

原因：本项目的数据量是单人规模，当前瓶颈是流程可见和采集留痕，不是服务吞吐。引入数据库和队列会先增加维护成本，而不是先增加产出。

## 3. 本项目落地版本

保留 Node 内置能力和本地 JSON，不新增依赖：

| 能力 | 实现 |
| --- | --- |
| 定时检查 | `npm start` 后服务端每 60 秒做一次 due tick |
| 档期 | 每天 / 每周，默认围绕 `settings.collectionTime` |
| 到期规则 | 只运行启用的每日 / 每周任务；按需和仅研究不跑 |
| 自动方法 | `public-rss`、`public-page` |
| 人工方法 | `manual`、`browser-assisted`、`platform-export` 到期后生成 blocked 提醒 |
| 失败处理 | 5 分钟起步指数退避，最长 6 小时 |
| 成功处理 | 失败计数清零，回到正常档期 |
| 并发保护 | 同一 source 同时只允许一个运行 |
| 状态字段 | `nextRunAt`、`failureCount`、`lastCollectionError`、`automationStatus` |
| 安全开关 | 页面可暂停 / 恢复；环境变量 `AUTOMATION_ENABLED=false` 可整体关闭 |
| 常驻入口 | `npm run setup-task` 安装当前用户登录任务；`npm run remove-task` 移除 |
| 手动入口 | `POST /api/automation/tick`，`npm run collect` 只跑到期任务 |
| 强制入口 | `npm run collect -- --force` 或页面“强制检查全部” |
| 本地投递箱 | `drops/` 默认每 30 秒扫描，JSON / Markdown / TXT 自动解析、去重、入库和归档 |
| 快速粘贴 | `POST /api/capture` 解析 JSON / 普通文本，自动识别 URL、标题、互动数和热评 |
| 公开页面 | 解析 Open Graph、JSON-LD、canonical 和同站链接，不再只保存快照 |
| 多层去重 | 规范化链接、平台内容 ID、作者 + 标题、标题 + 发布时间 |
| 自动晨报 | 到达 Inbox 时间后汇总高潜力信号、待人工账号、重试账号和下一步动作 |

浏览器辅助账号不会被伪装成无人值守采集。系统到点只生成 `blocked` 和下一步人工动作，仍然遵守现有边界：不自动滚动、不调用平台私有接口、不使用登录态后台请求、不绕过风控。

## 第二层：本地投递箱与晨报

投递箱和快速粘贴解决的是“进料后自动化”，不是绕过平台限制。浏览器辅助结果、平台导出、手工复制的热评和外部工具输出都可以进入统一通道，服务端做格式解析、身份去重、互动基线计算、快照留痕和运行记录。

晨报只做汇总，不替用户丢弃内容。高潜力、值得观察和待补数据是排序提示，最终去向仍由人在 Inbox 判断。

## 4. 后续扩容原则

1. 新增平台先补 adapter，不新增第二套调度系统。
2. 公开 RSS / 页面 / 官方导出优先进入 L2。
3. 登录强、风控强的平台停留在 L1 人工确认，不为了“全自动”冒封号风险。
4. 当单次 tick 经常超过一分钟或信源数量明显增加，再评估独立 worker；当前不预支复杂度。
5. 登录常驻任务只启动本地 Node 服务，不启动浏览器、不访问平台登录态。
